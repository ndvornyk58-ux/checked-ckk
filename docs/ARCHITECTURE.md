# Архитектура Cookie Inspector Pro

Документ описывает устройство приложения и правила, которые проверяются автоматически.
Обоснования ключевых решений — в `docs/adr/`. Текущее состояние реализации — в `docs/STATUS.md`.

## 1. Назначение и границы

Локальная desktop-платформа для разбора, проверки, аудита безопасности и учёта HTTP cookies
**собственных** приложений и тестовых сред. Все данные обрабатываются локально; cookies никуда
не отправляются, кроме явно настроенного и подтверждённого endpoint'а диагностики (ADR-0004).

Вне границ продукта (не реализуется архитектурно, а не только «не рекомендуется»):
проверка чужих аккаунтов, массовая проверка импортированных cookies на сторонних сервисах,
обход MFA/CAPTCHA, расшифровка значений, защищённых браузером средствами ОС (ADR-0005).

## 2. Слои

```
app.gui            PySide6: окна, Qt-модели, темы             ─┐
app.workers        очередь задач, пул процессов, чекпоинты      │ направление
app.services       сценарии использования (use cases)          │ зависимостей
app.infrastructure БД, крипто, ФС, браузеры, HTTP, плагины      │ только вниз
app.parsers        потоковые парсеры форматов                   │
app.rules          движок правил + наборы правил                │
app.domain         модели и перечисления (чистый Python)       ─┘
app.bootstrap / app.cli / main.py — composition root, вне слоёв
```

Инварианты (проверяет `lint-imports`, тест `tests/test_architecture.py`):

1. Модуль может импортировать только модули своего слоя или ниже.
2. `app.gui` не импортирует `app.infrastructure`, `sqlalchemy`, `alembic` — только сервисы и домен.
3. `PySide6` разрешён только в `app.gui`.
4. `app.domain`, `app.rules`, `app.parsers` не зависят от хранилища.

Нарушение любого пункта роняет тесты — граница держится механически, а не дисциплиной.

## 4. Модель данных

Доменная `Cookie` — неизменяемый `slots`-dataclass (ADR-0007). Ключевые решения:

* `domain` нормализуется (нижний регистр, без ведущей точки); признак host-only хранится отдельно.
* Все отметки времени — с часовым поясом (UTC); «наивное» время отвергается конструктором.
* `value` — `SecretValue`: `str`/`repr`/`format`/логирование всегда маскируют значение.
* `value_state`: `present` / `browser_encrypted` / `absent` — значение может честно отсутствовать.
* `identity` = (name, domain, path, host_only, partitioned) — ключ дубликатов по RFC 6265 §5.3.

Схема БД (миграция `0001`):

| Группа | Таблицы |
|---|---|
| Рабочее пространство | `projects`, `settings`, `key_store` |
| Импорт | `import_batches`, `source_files`, `import_errors` |
| Cookies и анализ | `cookies` (+ `cookies_fts`), `analysis_runs`, `findings` |
| Диагностика | `diagnostic_endpoints`, `diagnostic_runs` |
| Фоновые задачи | `jobs`, `job_tasks` |
| История и удобство | `operations`, `saved_filters`, `presets`, `plugins` |

Хранение значения: `value_ciphertext` (nonce‖шифротекст‖тег), `value_hmac` (ключевой HMAC для
дубликатов без расшифровки), `value_length`. Открытого значения в БД нет (ADR-0003).

Время в БД — целые секунды Unix UTC. Индексы составные с `project_id` первым, под
keyset-пагинацию и фильтры Cookie Manager. Поиск по подстроке имени/домена — FTS5 c
токенизатором trigram, синхронизируется триггерами (ADR-0002).

## 5. Потоки данных (целевые)

**Импорт:** файл → определение формата (оценка уверенности) → потоковый парсер → `Cookie`
→ шифрование значения + HMAC → пакетная вставка → валидация → статистика и ошибки по строкам.
Файл никогда не загружается в память целиком.

**Валидация/анализ:** выборка чанками → `RuleEngine` → `Finding` → запись находок и
сведённого статуса (`ValidationStatus.worst`, максимум `Severity`) → `analysis_runs`.
Хранятся находки только последней проверки каждой cookie; агрегаты всех запусков остаются
в `analysis_runs` (основа для сравнения «до/после»).

Сведение к статусу: находки валидатора дают статус напрямую; находки безопасности
отображаются как HIGH/CRITICAL → SECURITY_ISSUE, MEDIUM → WARNING. Упавшее правило
превращается в находку UNKNOWN — ошибка видна в результате и в журнале.

**Транзакционность импорта:** весь пакет пишется одной транзакцией, поэтому отмена
откатывает его целиком. Ошибка одного файла не прерывает пакет: файл получает статус
`failed` или `partial` (записи до места повреждения сохраняются).

**Диагностика:** endpoint из allowlist (`local` или `verified`) + одна тестовая сессия → запрос
→ сравнение с ожидаемыми маркерами → `diagnostic_runs`. Пакетного сетевого режима нет.

## 6. Конкурентность

GUI-поток никогда не выполняет I/O и вычисления. I/O — `QThreadPool`, CPU — `ProcessPoolExecutor`
(парсинг и анализ чанками; между процессами передаются пути, смещения и ID, а не большие объекты).
Каждый процесс открывает своё соединение с БД; запись сериализуется через сервисный слой.
Pause/resume/cancel — кооперативные, на границах чанков; состояние в `jobs`/`job_tasks` (ADR-0008).

## 7. Безопасность данных

* Значения cookies — только шифротекст в БД; ключ данных обёрнут ключом из keyring ОС
  или из мастер-пароля (scrypt).
* `SecretValue` исключает случайную утечку через строки и логи; SQL-эхо выключено.
* Экспорт по умолчанию маскирует значения; открытый экспорт — явное подтверждение +
  повторная аутентификация + пометка в отчёте.
* Тест-«ловушка»: импорт файла с уникальным маркером и поиск маркера во всех логах и экспортах.

## 8. Каталоги данных

`CIP_DATA_DIR` → портативный режим (`portable.flag` рядом с приложением → `./data`) →
каталог пользователя ОС. Портативный режим ничего не пишет в профиль пользователя.

## 9. Качество

`scripts/check.sh` / `scripts/check.ps1`: ruff, ruff format, mypy (strict для domain, rules,
parsers, services), import-linter, pytest. Фаза не закрывается, пока проверки не зелёные.
Тест `test_migration_matches_orm_exactly` не даёт ORM и миграциям разойтись.
